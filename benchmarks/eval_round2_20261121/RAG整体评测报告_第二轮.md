## 三、本轮新发现的问题

### A.（P1）比较通道解析器：数词短语并入项目名

**现象**：CX01「星云**和天枢两个项目**的负责人分别是谁？…」、CX03「星云、天枢、北斗三个项目的预算加起来…」、CX07「天枢、昆仑、沧海三个项目的负责人…」全部返回「无法确认所有要比较的项目，请核对项目名称。」

**根因**（已用单元探针复现）：`parse_project_comparison` 的边界正则把「A 和 B 两个项目的负责人」切成 `names=('星云', '天枢两个项目')`——最后的数词短语「两个项目」没有从项目名里剥掉，`resolve_project_filter('天枢两个项目')` 抛 ValueError → 整题拦截。而「四个项目**里**」句式（CX02）因命中 `count+项目+里` 边界正常工作。

**影响**：最自然的中文问法（「A和B两个项目的…」）恰好落在 bug 上；解析成功时通道本身表现很好（CX02 18.3s 正确完成四项目极值）。
**建议**：解析 names 后对最后一个名字剥掉尾部 `数字+项目` 短语（与 `_PROJECT_SUFFIX` 同理）；或把 `的(?=负责人|预算)` 边界优先于数词短语匹配。

### B.（P1）「证据支持检查」门禁误拦正确答案

**现象**：SN06「沧海项目是什么时候通过验收的？」（3.0s）、MD20「华信合同约定的设备交付时间是什么时候？」（46.1s）都返回「找到了候选资料，但没有足够证据支持这个问题。」——**而检索实际已命中正确文档**（探针确认：沧海验收报告在 project 过滤下 rank1 召回；华信合同 Top1）。

**根因**（`src/evidence_support.py`，两个独立缺陷）：
1. **日期窗口过窄**：`field_value(..., before=14)` 只回看关键词前 14 字符。沧海报告原文「项目于 2025-07-15 通过客户验收」中，日期距「验收」15 字符——差 1 个字符被漏判 → `missing=['验收日期']` → 硬拦截；
2. **锚点/取值仅支持中文**：华信合同是英文 PDF（"deliver all equipment before 2024-09-30"），锚点正则 `交付|交接` 不匹配 "deliver" → 交付日期判定失败 → 拦截。第一轮跨语言 PDF 题（S04/MD12/SN07 等）能通过是因为问的是编号/金额/期限（未被该门禁覆盖）。

**建议**：① `before` 放宽到 30~40 字符（或按句级对齐而非字符窗口）；② 锚点词表补英文（deliver/signing/effective/acceptance）或对非中文文档跳过该门禁；③ 门禁从「硬拦截置空上下文」降级为「提示证据可能不支持，由生成端声明不确定性」——当前把已召回的正确证据整个丢掉，代价过高。

### C.（P2）枚举通道提取召回缺口（残余）

- CX04：三份文档进入提取，只产出 2 条记录——天枢立项报告的「项目预算：200 万元」未被提取（答案缺失 200 万）；
- CX15：代表文档选择把「昆仑项目启动新闻.html」（内容是 300 家工业客户）当成昆仑项目的代表，昆仑立项报告（预算 300 万）未进入提取 → 无法回答预算极值；
- CX20：12 批提取达到模型调用预算，仅提取出 1/3 个相关项目。

共性：候选文档选择/批量提取在小预算下覆盖不足。与第一轮 C08 同类，已有首行不完整声明（F4 修复），但**完整性本身**仍受 `enum_max_calls`（12 次）与代表文档排序制约。建议：按项目/实体聚类的代表文档选择（立项报告优先级高于新闻页），预算内未覆盖的候选在 coverage 中逐个点名。

### D.（P3）判分校准说明（评测方问题，非系统问题）

重判时修正了三处判分校准（详见 `regrade.py`）：①答案含千分位逗号「15,999」因 norm 未去逗号被误判（CX17 答案本身正确）；②SN15 的「无法识别所指定的检索范围」按设计内诚实拒答计通过；③MD07 枚举模板「3 条带原文证据的记录」计为有效计数。修正后成绩 **52/60=86.7%**；真实失败为 8 题（SN06/MD20/CX01/CX03/CX04/CX07/CX15/CX20）。

### E.（观察）纯代词追问未注入会话项目过滤

「星云项目的里程碑有哪些？」→「**它**的立项预算是多少？」：`project_reference` 只识别「这个/该/当前+项目」类指代，「它」不触发会话项目 ID 注入（filters 无 project_id）。本次仍答对（135 万，语义召回 rank1 命中星云章程），正确性靠召回兜底而非范围限定。建议 `conversation_project` 的触发条件补充纯代词（它/该项目/上述项目）。

## 五、性能（第二轮）

**分难度端到端**：简单 8.4s（p50 6.9）/ 中等 18.4s（p50 7.7）/ 复杂 22.1s（p50 22.5）；全卷平均 16.3s，最大 91.7s（MD18 财务细则，本地精排 8s+ 叠加）。

**分通道耗时**（90 卡片库）：

| 通道 | 典型耗时 | 说明 |
|---|---|---|
| 普通问答（QU+混合检索+本地精排+生成） | 3~15s | 精排仍占 5~8s 为大头 |
| 项目比较通道（无生成，结构化渲染） | 3.3~18.3s | 随分支数增长；CX02 四项目 18.3s |
| 指定文档枚举 | 4.9~8.5s | 快（文档定位+单文档展开） |
| 跨文档枚举（分批提取） | 18~58s | 12 批调用预算触顶是常见停止原因 |
| 缓存命中 | 0.005s | 同配置重复问题 2000× 加速 |

**基础设施**：Query Embedding 0.39~0.44s（较第一轮 0.12s 变慢，与 Ollama 当时机负载相关）；Qdrant 检索 14~31ms；BM25 冷启动 1.54s / 热查询 85ms。Qdrant/embedding 在当前量级仍不是瓶颈，**本地精排与枚举批调用的成本控制**依旧是最值得优化的两处。
