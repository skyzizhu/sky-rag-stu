# 检索设置上下文预算评测报告（context_max_tokens × context_max_per_doc）

**日期**：2026-11-26 ｜ **分支**：dev/v3.9
**背景**：检索设置页新增「上下文长度上限（1000~8000）」与「单文档最多采用（1~10）」两个滑杆（V3.9.2），
仅作用于 Web 普通问答；枚举通道保持自身预算（40 条/12000 tokens）不跟随，MCP 渠道不受影响。
**目的**：验证不同设置值下的回答正确性、延迟与实际上下文规模，确认不存在"调错值答错题"的风险区间。

## 一、评测设置

- **题集**：Web 渠道 6 道复杂题（W02 多条件审批链 / W03 跨字段算术 / W04 时效规则 / W06 角色职责枚举 /
  W08 生命周期聚合 / W10 违规处理交叉），评分沿用双渠道评测同一口径（answer_must/must_not/sources_any）。
- **配置矩阵**：9 组 = 基线 4000/3 + token 单维（1000/2000/8000）+ per-doc 单维（1/2/5）+ 双维极值（1000/1、8000/5）。
- **入口**：`answer_question(top_k=5, context_max_tokens=X, context_max_per_doc=Y)` —— 与 UI 检索设置
  同一参数链路（设置页 → session → answer_stream）。

## 二、结果总览：**54/54 轮全部通过（9 组 × 6 题）**

| 配置 | 通过 | 平均耗时 | 上下文均值（实际） | 说明 |
|---|---|---|---|---|
| 基线 4000/3 | 6/6 | 13.1s | 2846t | 当前 .env 默认 |
| token 1000/3 | 6/6 | **9.6s** | 842t | 最省：上下文被压到 ~850t，仍全对 |
| token 2000/3 | 6/6 | 11.8s | 1693t | |
| token 8000/3 | 6/6 | 13.4s | 3590t | 放宽后携带更多（W08 达 6217t） |
| per-doc 4000/1 | 6/6 | **9.6s** | 2641t | 单文档限 1 张：多文档题上下文变薄（W10 -30%） |
| per-doc 4000/2 | 6/6 | 12.0s | 3660t | |
| per-doc 4000/5 | 6/6 | 12.6s | 2940t | |
| 双苛刻 1000/1 | 6/6 | **9.7s** | 842t | 最苛刻组合仍全对 |
| 双宽松 8000/5 | 6/6 | 16.5s | 3391t | 最慢（W03 出现一次 40s 生成波动） |

## 三、结论

1. **不存在"调错值答错题"的风险区间**：从最苛刻的 1000 tokens/单文档 1 张到最宽松的 8000/5，
   54 轮全部通过——当前语料下这些问题的答案证据都很小，预算宽容度大。
2. **两个滑杆均真实生效**：token 上限直接控制实际携带量（1000 档均值 842t vs 8000 档 3590t，
   8000 档未撑满是候选本就有限）；单文档限额主要影响多文档题的证据多样性（per_doc=1 时 W10 上下文 -30%）。
3. **延迟与成本符合直觉**：苛刻档最快（输入少，平均 9.6s）、宽松档最慢（平均 16.5s）。
   token 调大 = 回答成本与耗时线性上升，与设置页 help 文案一致。
4. **推荐默认维持 4000/3**：通过率与极值档相同，而资料丰富度显著优于 1000 档；
   用户如追求更快响应可自行下调，属个人偏好而非正确性需求。

## 四、评测期间发现并修复的真实缺陷

**QA 缓存键未包含预算参数**：缓存键 `answer_budget` 段只读 `.env` 全局配置——用户在检索设置里
改变预算后重问同一问题，会命中旧预算的缓存答案（新设置形同虚设）。已修复：UI 覆盖值并入缓存键
（无覆盖时回落全局值，不造成既有缓存失效）。首跑评测正是靠该缺陷暴露（8 组配置 0.0s 缓存命中）。
