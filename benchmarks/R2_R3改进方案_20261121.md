# R2 / R3 改进方案（基于业内调研 + 本仓库根因分析）

> 2026-11-21 · 依据第三轮评测失败根因 + 业内实践调研。R2=长文档多事实上下文覆盖；R3=docx 章节元数据丢失。
> 调研来源见文末。

---

## 〇、根因修正（先纠正第三轮报告的一处表述）

第三轮报告 M-1 写的是「docx 标题样式未生成 section」。**本轮逐步调试发现真实链路是**：

```
docx Heading 样式 → parser 正确转成 "# 一、xxx" ✅（src/parser.py:_docx_paragraph_line）
"# " 标题行 → chunker._split_by_sections_raw 正确切出 7 节 ✅
7 个小节（各 60~100 字）→ _merge_short_sections：累计未超单卡容量 640 token
   → 【全部合并成 1 张卡】，section 取组内第一节（文档开头无标题 → None）❌
```

即：**标题转换和切分都正常，是"短小节合并"策略吞掉了章节边界**。该策略 2026-11-08 为网页碎块引入（Xtools 价格区 5 个碎块各自成卡的问题），对网页剪藏是对的，但对结构化文档（docx 手册/需求书）过度合并。这个修正让 R3 的改法完全不同——不需要动 parser，只需要动合并策略。

R2 根因维持第三轮结论：`CONTEXT_MAX_PER_DOC=3`（每文档最多 3 卡进上下文）+ 精排后取舍，多事实题需要同一文档第 4+ 张卡（slide1 日期、slide3 价格、slide4 渠道）时被名额挤出。

## 一、业内做法盘点

### R2：长文档多事实 / 上下文组装

| 技术 | 核心思想 | 与本系统的契合度 |
|---|---|---|
| **Anthropic 上下文检索**（Contextual Retrieval） | 给每张卡片拼上"文档标题+章节+简述"再向量化+BM25，检索失败率 -35%（+BM25 后 -49%） | ★★★ 高——卡片文本已有「来源文档：」前缀（半成品），补章节/项目即达同样效果，且**确定性拼接零 LLM 成本** |
| **Parent-Document / Small-to-Big** | 用小单元检索（准），返回大单元给模型（全） | ★★★ 高——本系统已有枚举通道的 `expand_documents`（整文档展开），普通问答缺这一步；已有相邻卡拼接（半成品） |
| **Sentence Window** | 句子级检索 ±N 句窗口返回 | ★★ 中——本系统卡片粒度(640)已大于句窗，收益有限，且要重建索引 |
| **多跳迭代检索**（ReSP 等） | 检索→推理→再检索，直到补齐 | ★ 低——枚举 stage2 已有补查轮；普通问答引入迭代会显著加延迟（当前精排已占 7~8s），性价比差 |
| **Graph-RAG / RAPTOR** | 文档图/摘要树 | ★ 低——重架构，当前 116 卡规模远不需要 |

### R3：结构化切片 / 章节感知

| 技术 | 核心思想 | 与本系统的契合度 |
|---|---|---|
| **Heading-Aware Splitter**（LangChain MarkdownHeaderTextSplitter 等业界共识） | 切分尊重文档自身标题层级；**短节可合并，但合并块要记录覆盖的章节范围** | ★★★ 高——chunker 已按标题切分，只差合并时保留章节信息 |
| python-docx `paragraph.style.name` 提取 Heading 1/2/3 → 转 Markdown 层级 | 标题→`#`→结构切分 | 已实现（本次调试确认），无需动 |
| 结构感知解析器（unstructured / DocLing / LlamaParse） | 版面级解析 | ★ 低——引入重依赖，当前 python-docx 已够用 |

**结论：两项都选最贴合现有架构的路径，不引新依赖、不换架构。**

## 二、R2 方案（分 3 步，按投入产出排序）

### R2-a.【快赢】上下文拼接信息补全（查询时，零重建）
**改 `src/context.py` 的 `citation_label`**：普通问答（非仅枚举）的资料附页行，从现在的「[1] 文件名」扩成「[1] 文件名｜章节路径｜页码」。S18/C13 失败的另一半原因是模型拿到 slide 卡片却不知道"这是发布会第 1 页的日期卡 vs 第 3 页的价格卡"，信息标注补全后生成端定位能力提升。
- **改动**：仅 `context.py` 展示层，~20 行；无入库/索引影响
- **验收**：C12/C13 答案能区分"标准版/旗舰版"价格来源页

### R2-b.【主修】多事实题的"主导文档扩展"（Small-to-Big 落地）
**改 `src/pipeline.py` 普通问答组装段**：复用枚举通道已有的 `expand_documents` 思想——精排完成后，若满足以下条件，把"主导文档"的全部卡片拉进候选（仍受总 token 预算约束）：
- 触发条件：`sub_queries ≥ 2`（QU 拆分）**或** 精排后 Top-5 中同一文档卡片 ≥2 且该文档总卡数 ≤ 12（小文档整体装入）
- 行为：`ctx_max_per_doc` 从 3 动态放宽为该文档全部卡片；总名额与 `CONTEXT_MAX_TOKENS` 不变（挤占的是低分旁证的名额，不是预算）
- **这是把枚举通道已经验证过的"文档展开"机制下沉到普通问答**，不是新发明

**改 `src/context.py` build_context**：`max_per_doc` 参数支持 `None=不限`（枚举通道已这么用），普通通道按上述条件传入动态值。

- **改动**：pipeline.py ~40 行 + context.py ~10 行
- **验收**（第三轮失败题全绿）：S18（slide1 日期）、C12（slide3 价格 19999）、C13（日期+价格+续航+渠道四事实）、C11（规格书 14 位密码卡）
- **风险**：长文档（如 79 卡）不会触发（卡数 ≤12 才扩展）；误扩展最多多带几张低分卡，总预算兜底
- **参数**：`.env` 新增 `EXPAND_DOC_MAX_CARDS=12`（可调 0=关闭）

### R2-c.【检索增强】章节上下文拼进卡片文本（入库时，需重建窗口）
Anthropic Contextual Retrieval 的确定性版：**入库切片时**，卡片文本前缀从「来源文档：X」扩为「来源文档：X｜章节：A>B>C｜项目：星云项目」再向量化+BM25。
- **收益**：跨卡语义锚定（"500 元"带上"差旅住宿标准"章节语境），BM25 命中章节名词；对应 Anthropic -35% 检索失败率的量级
- **代价**：**卡片文本变化 = 内容指纹变化 = 全库版本 +0.1 重入库**（你们机制决定）。不能在线做
- **建议**：与 R3-b 的切片策略变更**合并到同一次全库重建**执行（一次重建吃两个收益）；实现本身 ~15 行（chunker 拼 metadata 前缀）

> R2-a + R2-b 预计解决第三轮 3~4 个失败题（81.7%→~88%）；R2-c 属检索质量的长线投资，绑重建窗口。

## 三、R3 方案（分 2 步）

### R3-a.【小改】合并组保留章节信息（不动卡片结构）
**改 `src/chunker.py` 的 `_merge_short_sections`**，两个行为修正：
1. 组内 leaf 为 None（文档开头段）而组内后面有真实章节时，**取第一个非空章节名**，并在正文保留小标题（现已保留 ✅）
2. 合并组跨越多个章节时，chunk metadata 新增 `sections: ["一、总则","二、考勤与作息",...]` 列表（现有 `section` 字段保持首节，兼容下游）

- **改动**：~25 行；**不需要重入库**（只影响下次入库的新卡片；存量卡可随下次重建刷新）
- **验收**：第三轮 M-1 矩阵的 sections 检查翻绿；来源列表能展示章节

### R3-b.【策略】结构化文档禁跨章合并（绑定重建窗口）
**改 `_merge_short_sections` 的分组规则**：当相邻两节的**标题层级相同**（如同为 H1 的"一、""二、"），不再合并——每个 H1 章节独立成卡（章节内小节仍可合并）；无标题文档（txt/网页清洗产物）维持现状。
- **理由**：业内 heading-aware splitter 的共识是"合并可以，但不能跨越语义边界到无法定位"；H1 通常是手册的"制度条款组"，一卡一章正好落在 640 容量附近（我们两份 docx 每章 80~150 字，一卡一章后单卡偏小——由 R2-c 的章节前缀补语境，配合 R2-b 的整文档扩展兜底完整性）
- **改动**：~20 行 + **全库重建**（卡片结构变化）；与 R2-c 同窗口执行
- **验收**：入库后 docx 卡片数 ≈ 章节数（培训手册 ~7 卡、需求书 ~5 卡）；S10/S11/C07 回归通过；重跑 60 题考卷无退步

### 不做的事（明确排除）
- 不引入 unstructured/DocLing 等重型解析器（python-docx 链路已验证正常）
- 不做句窗检索/Graph-RAG（当前规模收益不抵复杂度）
- 不动 parser（标题转换已正确）

## 四、实施顺序与验收总表

| 步骤 | 内容 | 改动量 | 需重建 | 验收 |
|---|---|---|---|---|
| 1 | R2-a 附页信息补全 | ~20 行 | 否 | C12/C13 页级定位 |
| 2 | R2-b 主导文档扩展 | ~50 行 | 否 | **S18/C12/C13/C11 全绿**；60 题回归无退步 |
| 3 | R3-a 合并组章节保留 | ~25 行 | 否（存量随重建） | M-1 矩阵翻绿 |
| 4 | R2-c + R3-b（合并窗口） | ~35 行 | **是**（全库版本+0.1） | 重入库→重跑 60 题→命中率 ≥91.7% 且多事实题改善；metadata 矩阵 docx 行全绿 |

步骤 1-3 可先行（半天内完成+回归）；步骤 4 单独排期（重建后建议顺手跑一轮全量评测对比）。
