# 代码结构与性能审查

本轮以当前开发分支和工作区的切片修复为基础，沿正常入口核对入库、向量库、Web 与 MCP 检索、同文档补片、管理档案和后台统计。验证数据使用临时台账、内存 Qdrant、测试向量和项目已有的本地精排模型。

## 已处理

| 环节 | 审查发现 | 改动 |
| --- | --- | --- |
| Qdrant 集合和索引 | 每次入库都会再次提交字段索引创建请求。向量搜索还会在实际查询前请求一次集合存在状态 | 读取集合的索引清单，只创建缺失或类型不匹配的索引。向量搜索直接执行查询，并把不存在的集合转成原有业务提示。 |
| 增量入库 | 文件指纹计算一次分配整份文件，跳过判断从向量库读取整套档案字段，并按某张代表卡的摘要验证版本 | 文件按 1 MiB 分块计算 MD5。跳过校验读取四个卡片字段，逐卡验证当前版本、状态与指纹。合并批量清理和同批权限组转换。 |
| BM25 | 缓存命中仍有重复集合检查。评分扫描所有卡片，再对全部匹配项排序 | 保留一次卡片数校验和权限纪元校验。分数使用原 BM25 公式，只给有命中词的候选计分，并用有界 Top K 选取。索引仍按检索范围和用户身份隔离。 |
| Qdrant 滚动读取 | 盘点、目录、关键词索引、老卡补片和工作台重复实现分页 | 统一内部页面读取并按各业务投影必要字段。目录统计只为被选中的文档计算一次密级。 |
| 同文档补片 | 同时存在旧枚举展开与现行补片，旧函数只被自己的测试调用 | 删除旧函数，把顺序、长文档边界和权限测试移到当前业务入口。现行普通问答、复合问答和枚举继续使用各自的证据预算。 |
| 后台 LLM 费用 | 汇总和分页只从最近 300 条原始日志计算，超过范围的有效条目被漏计 | SQLite 在同一读取快照内统计全部有效费用日志，只返回所请求的一页明细。保留账号与日期筛选、现价重算和分页接口。 |

## 对照数据

用 5000 张合成卡比较 Top 10，按五轮各 120 次调用的中值记录单次 CPU 时间。候选内容、BM25 得分和同分顺序逐项相等。

| 场景 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 250 张命中 | 2.950 ms | 0.463 ms |
| 5000 张命中 | 3.821 ms | 3.474 ms |

热 BM25 回归验证单次命中只调用一次集合计数，集合存在检查和卡片滚动均为零次。Qdrant 索引回归模拟服务端已返回完整字段索引，后续入库的建索引调用为零次。费用回归使用 306 条匹配日志，验证了全量费用汇总、末页和日期筛选。

同一份 6000 条临时费用日志中，按原日志接口循环分页后在 Python 汇总的对照耗时约 458 ms，SQLite 全量汇总并取 20 条明细耗时约 44 ms。双方汇总条数、调用和 token 数一致。这组对照使用完整统计范围，便于比较两种实现的处理成本。

最终 272 项隔离回归通过，上一轮切片、补片、MCP 与本地精排的 38 项对照也全部通过。后台汇总经临时数据库和直接接口调用验收。Windows 的测试隔离会阻止 HTTP 测试客户端初始化时的本地套接字连接。

本地模型、向量化服务和外部 LLM 的占比取决于部署环境及问题类型。这里测得的是 CPU 排序和数据库调用路径，整条问答链路的延迟需要在实际部署中按阶段评测。MCP 会话通过当次请求身份隔离，涉及身份和权限的开销以分段验收数据为依据。
