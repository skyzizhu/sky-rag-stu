## 一、这个项目是什么

**一句话**：一个跑在自己 Mac 上的私人问答系统。

- 把你的笔记、需求文档、会议纪要、网页剪藏放进 `knowledge/` 文件夹；
- 用自然语言提问，比如「chunk_size 初始设多少？」；
- 系统自动找出最相关的知识片段，让本地 Ollama 或云端大模型基于这些片段回答，并**标明每条答案出自哪个文件、哪一页**；
- 资料库里没有的内容，它会老实说不知道，不编造。

**支持的文件格式（9 类）**：

| 格式 | 扩展名 | 说明 |
|---|---|---|
| Markdown | `.md` | 笔记、文档，支持 Front Matter 声明元数据 |
| 纯文本 | `.txt` | 通用文本文件 |
| PDF | `.pdf` | 逐页解析并记录页码；**扫描版**（无文字层）自动整页 OCR；页面内嵌图片也会抽出识别（加密 PDF 不支持） |
| Word | `.docx` `.doc` | 标题样式自动转为章节标记，表格逐行读取；**内嵌图片自动 OCR** |
| Excel | `.xlsx` `.xls` | 每个工作表转为「Sheet 标题 + 表格文本」，公式取计算值 |
| PPT | `.pptx` `.ppt` | 逐页解析标题/文本框/表格/演讲者备注，页码进元数据；**页面图片自动 OCR** |
| WPS Office | `.wps` `.et` `.dps` | 金山文档文字/表格/演示（老格式）：经 LibreOffice 转换后按 docx/xlsx/pptx 解析 |
| 图片 | `.png` `.jpg` `.jpeg` `.bmp` | 整张图 OCR 识别（中英文） |
| HTML | `.html` `.htm` | 网页剪藏，自动去除脚本/样式 |
| RTF | `.rtf` | 富文本格式 |

> **doc / xls / ppt / wps / et / dps 解析**依赖系统安装 **LibreOffice**（转换到 docx/xlsx/pptx 后走标准解析器）：
> macOS `brew install --cask libreoffice`；Linux `apt install libreoffice`；
> Windows 安装后把 `soffice.exe` 所在目录加入 PATH。转换产物带指纹缓存，重复入库不重转。
> OCR 由 RapidOCR（PaddleOCR 模型的 ONNX 移植版）**本地离线**完成，中英文均可，
> 纯 CPU 运行；不想启用时在 `.env` 里设 `OCR_ENABLED=false` 即可一键关闭。

**第 7 种输入源：直接贴网址（插件）**

除了本地文件，在「插件」菜单安装「网页入库」插件后，可以在
「上传文档 → 🌐 添加网页」里直接粘贴 URL（支持 `http://` 和 `https://`，
不带协议头时默认按 `https://` 处理）：系统自动抓取网页正文、
剔除导航/页眉等噪音，默认保存到「参考资料」领域并入库为知识卡片——
和本地文件一样可被检索、引用，重复录入同一网址会走增量判断自动跳过。
机制详见「五、怎么用 → 网页入库（插件）是怎么工作的」。

**两种打开方式**：
- **当工具用**：日常知识问答，文档一入库，随问随查；
- **当教材学**：打开调试模式（默认开启），每次回答都附带完整的「RAG 节点时间线」——
  15 个节点逐个展示发生时间、做了什么、输入与输出，对照 [prd.md](prd.md) 的节点讲解，边用边学。

**技术组合**：

| 角色 | 用的什么 | 在哪里运行 |
|---|---|---|
| 开发语言 | Python | 本机 |
| 文档理解 | 自研解析模块 | 本机 |
| 知识向量化 | qwen3-embedding:4b（Ollama） | 本机，不联网 |
| 知识存放 | Qdrant 向量数据库 | 本机 |
| 回答生成 | 本地 Ollama，或兼容 OpenAI API 的云端模型（DeepSeek / Kimi / 智谱 / 通义 / OpenAI） | 本机或云端 |
| 关键词检索 | BM25（rank-bm25 + jieba 分词） | 本机 |
| 回答精排 | 本地 cross-encoder（bge-reranker-v2-m3 ONNX，CPU）或 LLM 重排，`RERANK_BACKEND` 切换 | 本机/云端 |
| 操作界面 | Streamlit 网页 | 本机 |

## 二、RAG 是怎么工作的（先看懂原理）

RAG = Retrieval-Augmented Generation，检索增强生成。整个系统就是两条流水线：

### 流水线 A：把知识「存」进去

```text
📁 你的文件
   ↓ ① 文档解析      —— 不管什么格式，统一读成「正文 + 档案卡」
   ↓ ② 清洗          —— 去掉乱码、多余空行、PDF 页眉页脚
   ↓ ③ 知识切片      —— 把长文档切成一张张「知识卡片」
   ↓ ④ 向量化        —— 给每张卡片算一组「特征指纹」
   ↓ ⑤ 存入向量库    —— 卡片连指纹一起存进 Qdrant 档案馆
```

### 流水线 B：把答案「问」出来（V2 增强后）

```text
❓ 你的问题
   ↓ ⑥ Query 理解/改写（V2）—— LLM 把口语化提问改写成检索友好查询，并推断过滤条件
   ↓ ⑦ 问题向量化    —— 问题也算成指纹（和文档用同一个模型）
   ↓ ⑧ 元数据过滤    —— 默认只搜「启用中」的知识；可手动限定领域
   ↓ ⑨ 混合检索（V2）—— 向量通道 + BM25 关键词通道两路召回，RRF 融合排名
   ↓ ⑩ Rerank 精排（V2）—— 本地 cross-encoder 或 LLM 打相关度分，精选 Top K
   ↓ ⑪ 资料组装      —— 排序、去重、相邻卡片拼接、标上出处编号
   ↓ ⑫ 提示词        —— 写一份「任务说明书」给大模型
   ↓ ⑬ 生成回答      —— 本地 Ollama 或云端大模型基于资料回答
   ✅ 答案 + 参考来源（文件 / 领域 / 章节 / 页码）
```

### V3.4 新增：复合问题查询拆分（Sub-Query）

一个问题包含多个信息需求时（如「查一下我的心得，并且查工作经历有几个」），
Query 理解会自动把它**拆成多个子查询**，逐个独立检索后合并去重，再精排精选——
避免混合查询"两个主题互相稀释"导致其中一个子问题的答案丢失。
拆分由 LLM 语义判断完成（不限措辞），单信息需求的问题不受影响。

### V3.5 新增：合并保底配额（Guaranteed Quota）

多个子查询的结果合并时，**每个子查询保底保留 Top N 条**进候选池
（N = max(3, 20 ÷ 子查询数)），剩余名额才按全局分数补足——
解决"全局排序、强者通吃"导致弱势子问题的证据在精排前就被挤光的问题。
能力边界：配额保"进候选池"；若某次 Query 理解没拆分（LLM 波动）配额无从生效，
主要失败源与 V3.6 方向记录在 rag_pitfalls.md 第 37 条与 realize.md B3.5.1。

### V3.6 新增：单题回答质量评估卡片

参考来源 / 调试信息下方新增「🔍 回答质量评估」卡片，对当前这条回答给出可信度参考：
① 结构信号（拆分触发、精排分数带、候选池→上下文、引用覆盖率、拒答一致性，0 次 LLM）；
② LLM 两维评审（忠实度/相关性，各 0~10 分，只分档优/中/差不设精确阈值）。
评估在回答输出完成后执行，不阻塞阅读；失败自动降级；设置页可关闭。
它与整卷评测互补：整卷管"批量回归"，单题卡片管"这一条回答可不可信"。

### V3.7 开发中：用户体系与知识权限（多用户）

登录（用户名+密码）+ 注册（选部门、密码两次确认）+ 独立 FastAPI 管理后台（端口 8700：
部门管理 / 业务方向 / 员工管理 / 重置密码 / MCP 访问令牌签发与吊销）。

后台「业务方向」支持创建多条独立业务方向，填写名称、英文/字母编号及备注；输入中文名称自动生成无声调拼音（如“智慧园区”→`zhihuiyuanqu`），可手动调整多音字或填写英文。名称、编号分别唯一，编号统一小写，同音名称可使用不同编号；记录持久保存在现有服务端 SQLite 的 `business_directions` 表中。此阶段仅管理清单，不关联权限部门或修改现有文档分类。

后台「项目管理」支持创建、查看和编辑项目。项目名称必填且唯一，主业务方向和牵头部门可留空，参与部门可多选。同一个部门可以参与多个项目。项目关系保存在现有 SQLite 的 `projects` 和 `project_departments` 表中，文档可见权限仍由各文档的可见部门设置决定。

上传文件、导入目录和网页入库都可以选项目，并显示项目当前的主业务方向。选项目时默认切到「项目」领域，也可手动调整。文档台账和 Qdrant 保存 `project_id`，主业务方向实时从项目主档读取。知识库管理可按项目或主业务方向筛选，也可给已有文档补挂、改挂或解除项目关联。编辑项目归属只更新元数据，无需移动原文件或重新向量化。

业务方向列表提供编辑入口，可修改名称、字母编号、备注，保留原 ID 和创建时间；编辑名称后自动生成拼音编号；在当前编辑中手动填写编号后保留手填值，清空编号可恢复自动生成，立即保存也会等待拼音生成完成。支持清空备注，重复名称/编号会被拒绝。编辑表单携带原始快照，其他管理员已修改时返回冲突，避免旧表单覆盖。成功及失败的编辑均进入管理员操作日志，成功记录对象 ID、名称/编号前后变化及是否更新备注。业务方向不提供删除按钮或删除 API。

后台「部门管理」仅填写名称和备注，不使用英文/拼音编号。部门创建后不支持编辑，仅支持启用、停用及符合条件时删除。员工按部门关联，文档按固定的部门权限键控制可见范围；升级时移除旧编号及其映射，保留部门 ID、名称、员工关联和现有资料权限。业务方向的拼音编号不受影响。

后台日志统一放在可展开/收起的一级菜单「日志」下，二级菜单为「管理员登录日志」「管理员操作日志」「员工登录日志」「员工检索日志」。管理员列表只管理账户，不再附带登录日志。管理员登录专页仅显示登录/登出及登录失败，支持账户/动作筛选、上一页/下一页和每页 20/50/100 条；员工日志与管理员日志保持分表读取。工作台的 RAG 日志快捷入口会自动展开对应菜单。

工作台显示部门、业务方向、员工和管理员数量，提供新增业务方向快捷入口；原最近登录区域替换为部门检索次数、Web/MCP 每日趋势，以及 RAG 检索入口次数、检索流程 LLM 调用环节统计，统一切换最近 7/30/90 天。请求按发生时的部门快照计数，包含 Web 问答和跨文档总结、MCP HTTP/stdio；缺失日期补零，零调用部门保留，匿名个人模式及管理员不计入员工统计。聚合直接扫描所选范围，不受列表 300 条上限影响。

新检索日志的 `usage.report_version=2` 表示本次采集：答案缓存命中不重放原回答用量，当次上下文摘要及回答评估仍分别计算；模型已返回用量但评估 JSON 解析失败的调用也保留。原回答的展示用量不变。LLM 统计仅包括本服务检索流程中有用量记录的调用，不含外部 MCP 客户端模型、Embedding、本地精排、入库自动标签或无用量的失败调用；按查询理解/精排/生成/摘要/列举/评估环节展示。缺少本次用量标记的历史记录单列参考，不并入可核验调用总数，也不按当前模型配置猜测历史模型。

后台「管理员操作日志」仅记录管理变更操作：部门的新增删除及启停、员工/管理员的新增编辑删除、业务方向的新增编辑、令牌签发吊销、服务启停/重启及这些操作的失败请求。管理员登录、登出、初始化认证仅写入管理员登录日志；列表查询、详情查看、状态轮询、日志查看和拼音预览不记录。之前产生的认证及查看类操作日志保留原始数据，但从操作日志列表和统计中排除。独立保存在同一 SQLite 的 `admin_operation_logs` 表中，保留当时的管理员 ID/账户、动作、对象 ID、安全摘要、时间、HTTP 结果、IP、UA 和耗时；账户删除后历史仍保留。服务控制成功表示控制指令已受理，实际运行状态由服务状态页确认。不保存原始请求/响应、密码、令牌、Cookie 或查询参数；校验失败只存通用失败原因，避免异常信息携带敏感输入。列表仅管理员可访问，支持账户/动作/结果筛选及 20/50/100 条分页，使用查询快照避免新日志插入导致翻页重复，刷新后展示最新记录。操作日志没有修改/删除接口；从本功能启用起统一记录，之前的零散记录仍保留在原管理员登录日志中，未记录过的历史无法补还。日志写入失败会在服务日志中报错，不阻断原管理请求。
### 三级密级与可见权限

入库或编辑文档时选择可见范围。密级由授权配置推导，归属部门 `department` 单独用于展示和筛选。

| 密级 | 授权配置 | 谁能查到 |
|---|---|---|
| 公开 | `allowed_groups=["all"]` | 全体员工 |
| 内部 | `allowed_groups` 为所选部门权限键 | 所选部门的员工，可多选部门 |
| 受限 | `allowed_groups=[]`，`allowed_users` 为所选用户名 | 授权名单上的员工 |

问答、管理页和 MCP 团队共享模式按登录员工的部门或本人授权过滤。MCP 从 PAT 验证员工身份。个人/离线模式可按原有模式访问本地知识库。旧卡片缺少 `allowed_users` 时仍按已有 `allowed_groups` 判断，全员可见的存量文档自动显示为公开，无需迁移。

修改名单只更新卡片档案和台账，无需重新向量化。停用员工会撤销其个人授权，重新启用后需手工重新授权。清理失败时账号保持停用，重新启用前会重试。最后一个受限授权被移除后，文档仍为受限，空名单对员工不可见。

### 每个节点在解决什么问题（白话版）

| 节点 | 干什么 | 为什么必须有 |
|---|---|---|
| ① 文档解析 | 9 类文件格式统一读出（含 OCR） | Word 和 PDF 长得完全不一样，得先统一 |
| ② 清洗 | 去杂质、保结构 | 脏文本会污染后面每一步 |
| ③ 切片 | 长文档 → 知识卡片 | 卡片越聚焦，搜得越准；整篇文档没法比对 |
| ④ 向量化 | 文字 → 特征指纹 | 让「意思相近」可以计算 |
| ⑤ 向量库 | 指纹 + 原文 + 档案一起存 | 千万张卡片也能毫秒级找相似 |
| ⑥ Query 理解/改写（V2） | 口语化提问 → 检索友好查询 + 推断过滤条件 | 「旧版笔记里写的多少」这种话，机器听不懂就搜不准 |
| ⑦ 问题向量化 | 问题也算指纹 | 才能和卡片指纹比对 |
| ⑧ 检索（混合，V2） | 向量通道 + BM25 关键词通道，RRF 融合 | 向量懂「意思相近」，关键词懂「一字不差」，互补 |
| ⑨ Rerank 精排（V2） | 本地 cross-encoder 或 LLM 打相关度分 | 粗排只看文字指纹，精排才理解内容 |
| ⑩ 资料组装 | 排序、去重、相邻拼接、标出处 | 给大模型一份干净完整的考卷附页 |
| ⑪ 提示词 | 立规矩 | 只准按资料答、不知就说不知、必须标出处 |
| ⑫ 生成回答 | 大模型组织语言 | RAG 的「G」：基于资料生成 |
| 引用展示 | 答案后面附来源 | 你随时能核对它说的是不是真的 |

> 💡 学习心法：每完成一个节点，标准不是「程序没报错」，
> 而是「我能看到这一步的输入和输出，并说出它解决了什么问题」。
> 项目里每个模块都可以单独运行打印结果，方法见「五、怎么用」。

## 三点五、知识库管理规范（V1.x 新增）

### 文件按领域存放

所有知识统一放在 `knowledge/` 主目录，一级目录对应领域：

```text
knowledge/
├── work/          💼 工作
├── learning/      📚 学习
├── life/          🌱 生活
├── projects/      📁 项目
├── reference/     📎 参考资料
└── archive/       🗄 归档       —— 归档目录里的内容默认不参与回答
```

上传文件时，选「学习」会直接保存到 `knowledge/learning/`。导入整个目录时，原目录结构会保存在该领域下。二级目录名不再生成子分类，三级目录名仍可提示主题。

已有文件保留原路径。入库台账和文档 ID 依赖该路径。旧文件显式声明的 `category` 及台账里的旧人工覆盖仍可读取。

### 文档类型（独立可选字段 `doc_type`）

`doc_type` 表示资料的文档类型，如「一期方案」「需求文档」「会议纪要」。它是独立于 `domain`（领域）、`topic`（主题）和 `file_type`（文件格式）的可选自由文本，不需要登记类型表。

- **取值优先级**：管理页人工指定（含显式清空） > Markdown Front Matter 的 `doc_type` > 上传时填写的默认文档类型 > 确定性自动推断 > 未分类。
- **自动推断**：从上传文件的原始目录由近到远查找明确的文档类型目录，保留命中的完整目录名称；无明确目录时，再从文件名识别一个明确的类型短语。不会调用 LLM 或根据正文猜类型；模糊、冲突或没有线索时留空。例如原目录 `总体方案/一期方案/材料.docx`、`总体方案/二期方案/材料.docx` 分别得到「一期方案」「二期方案」，不会都归成「总体方案」。
- **原始标签保留**：只去首尾空白，最多 80 个字符，不接受控制字符或非字符串；不转小写、不做同义词/别名合并。「总体方案」「一期方案」「二期方案」是不同标签，目录重命名或补类型不会合并不同文件的文档身份。
- **未分类兼容**：旧文档没有该字段、值为 `null` 或空字符串时，列表与来源返回 `doc_type: ""`；不迁移旧数据。新增 keyword 索引由现有入库建索引流程幂等安装，不在模块导入时连接服务。
- **筛选**：问答、管理列表与 MCP 可按类型精确过滤；省略/留空或 `all` 表示不限类型，`__unclassified__` 是仅供筛选使用的保留值，匹配缺失/`null`/空字符串，不能作为文档类型存储。类型筛选始终叠加既有领域、状态、版本和部门权限约束，不改变检索评分、精排或安全规则。

### 归属部门（独立元数据字段 `department`）

归属部门表示资料属于哪个部门，**不等于可见权限 `allowed_groups`**。例如资料归属研发部，但可见部门设置为全员，其他部门仍然可以检索；反过来，只给财务部权限的文件，也不会因为填写了研发部归属就对研发部开放。

- 文件上传、目录导入、网页收录均使用单选部门列表，来自后台启用中的部门，默认选择上传者本人部门；无有效部门时显示「未指定」。
- 优先级：管理页人工设置（包括明确清空） > Markdown 的 `department` 声明 > 上传选择 > 未指定。归属不从目录、文件名或正文猜测。
- 归属名称随卡片写入，同时在入库台账的 `department_info` 保存来源；重新入库、归档恢复、网页刷新与重建保留归属。重复跳过不会偷偷修改既有归属。
- BM25 的索引文本加入归属部门，因此正文未写部门名时，也能按部门名召回其资料。**本轮不增加 Query 理解部门推断**；自然语言命中是关键词召回，不等于强制按部门限定结果。需要精确范围时使用检索设置或 MCP 的 `department` 参数。
- 管理页可显示、筛选及独立修改归属。MCP 内容工具返回 `department`；`department="__no_department__"` 仅筛选未指定，省略/空白/`all` 不限制部门。
- 老文档缺该字段仍可正常使用并显示「未指定」，不批量迁移。

### 每张知识卡片都有一张完整「档案」

统一元数据包括 document_id（按路径生成）、chunk_id（卡片编号，如 `doc_a913bc12_0001`）、来源、路径、领域、主题、标签、章节路径、页码、版本、状态和各时间戳。

### 文件版本

入库时支持以下文件命名规则，版本统一用点号分隔（大小写不敏感，全角字符先规范化）：

| 文件名示例 | 提取版本 |
|---|---|
| `方案_v1.2.pdf`、`方案_V_1_2.pdf`、`方案_v_1_2.pdf` | `1.2` |
| `方案_ver_1_2.docx`、`方案_version-1.2.docx` | `1.2` |
| `方案_版本_1_2.md`、`方案_版本号：1.2.md`、`方案_版次1.2.md` | `1.2` |
| `方案_第1_2版.md`、`方案_1.2版.md` | `1.2` |
| `方案_1_2.md`、`方案-1-2.md`、`方案（1_2）.md`（末尾数字） | `1.2` |
| `需求V2.0.1.docx`、`需求_v_2_0_1.docx` | `2.0.1` |
| `方案_V2.pdf`、`方案_第2版.pdf` | `2.0` |
| `方案_Ｖ＿０１＿０２.md` | `1.2` |

最多识别四段，每段最多三位数字；保留 `1.10` 与 `1.1` 的区别。纯日期、单个裸数字、章节式裸点号数字（如 `说明_1.2.md`）、不完整/多个冲突的版本标记不猜测。裸的 `1_2` 也可能是业务编号，属于按命名约定推断；建议新文件显式使用 `v1.2`。版本取值优先级为：管理页人工覆盖 > 文件名 > Markdown Front Matter > 自动编号。

### 文档声明版本（正式版本）

新增的 `document_version` 与现有入库 `Version` 独立：不改变切片编号、增量更新和原有版本递增规则。

- 自动识别明确的文件名版本标记，以及 PDF 第1页 / PPT 第1张 / Word 开头原生段落或表格中的独立声明，如 `文档版本：V1.2`、`版本号：2.0`；Markdown 文件头可写 `document_version: 1.2`（或已有的 `version` 声明）。TXT/RTF/HTML 仅检查开头文本。
- Word 没有可靠的物理分页信息：检查最多20个非空开头块、最多4000字符，遇到显式分页即停止；不会标成真实“第一页”。PDF/PPT 不越过第1页/张寻找声明，PPT 演讲者备注不作为版本依据。
- 多个明确来源一致 → 记录版本和依据；仅文件名有标记 → “仅文件名，未正文核对”；有冲突或仅OCR线索 → “待人工确认”，不静默选最大值；无声明 → “未声明”，没有可用范围 → “无可用开头信息”。
- OCR线索只供人工核对；Excel工作表数字、Office修订次数/PDF技术版本、自定义属性、软件版本和修订记录的最大版本，本轮不用于自动确认。
- 知识库管理列表显示“文档声明版本 / 版本核对”；详情可查看原文依据。编辑档案时填写版本并勾选“确认此文档声明版本”后保存；普通档案修改不等于确认版本。确认只对当前文件指纹及入库版本有效，内容变化后重新核对；归档/恢复也重新提取，不隐式继承旧路径确认。

- 确认请求必须携带页面所见的内容指纹，并匹配当前有效卡片；同文件名版本内容更新后，旧页面确认会被拒绝。手动修改现有入库 `Version` 时同步台账并撤销旧确认，重新显示检测结果，不将旧确认当成新修订的确认。

这一版不使用LLM识别版本、不修改源文件、不增加依赖或服务；不迁移旧数据。


没有显式版本时首次默认 `1.0`，同一路径内容指纹变化后沿用原来的 `+0.1` 规则；三段及以上版本递增最后一段。内容未变的重复上传默认跳过，强制重新入库保留当前版本和历史卡片。文件名已经标注版本时按标注值记录，内容修改不会额外增加版本号。文件名版本仅决定元数据，不将不同路径或不同名称的文件自动合并成同一文档；上传的副本文件按其实际落盘文件名识别。

### Markdown 可以自定义元数据（Front Matter）

在 md 文件开头写一段声明，优先级高于目录推断：

```markdown
---
title: 我的标题
doc_type: 需求文档
topic:
  - RAG
  - 向量数据库
tags:
  - Chunk
  - Embedding
version: "1.0"
---
```

### 检索范围由你控制

- **默认只搜「启用中（active）」的知识**：丢进 `archive/` 的内容自动退居二线，不再参与回答；
- 检索范围可切换「仅 active / 包含归档 / 仅归档」，可限定某个领域；
- 命令行同样支持：`python -m src.retriever "RAG" --domain learning --status archive`。

### 知识管理

除了入库和检索，系统还内置了知识的管理能力：查看每个文件的档案与卡片原文、按关键词/领域/状态筛选、单文件重新入库、归档（退出日常检索）、恢复和一键清空重建。文件支持单选或批量选择后执行两种移除操作：**仅移除向量知识（保留磁盘文件）**，或**同时移除向量知识并删除磁盘文件**；删除最后一个文件后，已经没有其他文件的二级目录也会自动清理。所有移除操作都需要二次确认。

## 四、从零到跑通（安装步骤）

### 你需要准备

- 一台 Mac（Apple Silicon 或 Intel 均可）
- Python 3.10 或更新版本
- [Ollama](https://ollama.com)（已安装并可运行）

> Windows / Linux 用户：只有 Qdrant 安装一步不同（推荐改用 Docker），其余步骤一致。

### 第 1 步：下载项目 + 创建虚拟环境

```bash
cd sky-rag-stu
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### 第 2 步：填配置文件

```bash
cp .env.example .env
```

打开 `.env`，在下面两种方式中选择一种。

#### 方式 A：使用本地 Ollama 大模型（隐私优先）

先下载一个聊天模型，例如：

```bash
ollama pull qwen3:14b
```

然后填写：

```text
LLM_BASE_URL=http://localhost:11434/v1
LLM_MODEL=qwen3:14b
LLM_API_KEY=ollama-local
```

`ollama-local` 只是 OpenAI 客户端需要的占位值，不是真实密钥，也不会产生费用。你也可以把
`qwen3:14b` 换成其他已通过 `ollama pull` 下载、支持聊天的模型。

#### 方式 B：使用云端大模型（以 DeepSeek 为例）

```text
LLM_API_KEY=sk-你的key
LLM_BASE_URL=https://api.deepseek.com/v1
LLM_MODEL=deepseek-chat
```

其他服务商只需换后两行，对照表见 `.env.example` 里的注释。
**`.env` 已被 git 忽略，不会被开源出去，放心填 Key。**

### 第 3 步：准备本地向量化模型

```bash
ollama pull qwen3-embedding:4b
```

（如果你已经装过，跳过。）

### 第 4 步：安装并启动向量数据库 Qdrant

```bash
bash scripts/install_qdrant.sh    # 只需运行一次，下载约 40MB
bash scripts/start_qdrant.sh      # 每次使用前启动；停止按 Ctrl+C
```

启动后浏览器打开 <http://localhost:6333/dashboard> 能看到控制台，就说明成功了。
数据保存在 `storage/qdrant_data/`，重启电脑不丢。

> 备选方案：如果你更习惯 Docker，也可以
> `docker run -d -p 6333:6333 -v $(pwd)/storage/qdrant_data:/qdrant/storage qdrant/qdrant`，
> 效果完全一样。

### 第 5 步：环境自检

```bash
python check_env.py          # 基础检查，不花 API 的钱
python check_env.py --with-llm   # 顺手真实调用一次大模型，验证 Key
```

每一项都会显示 ✅ / ⚠️ / ❌ 和修复提示，全绿了再往下走。

### 第 6 步：把知识入库

项目自带 6 个「示例_」开头的示例文件（覆盖全部 6 种格式），可以直接体验：

```bash
python ingest.py             # 入库 knowledge/ 里的全部文件
# python ingest.py --rebuild # 想清空重来时用
```

### 第 7 步：打开界面，开始提问

```bash
streamlit run app.py
```

浏览器会自动打开页面：先去「📤 上传文档」确认 6 个示例已入库，
再到「💬 知识库问答」随便问，比如：

- 「知识切片的 chunk_size 初始建议设多少？」
- 「卡片笔记法的核心是什么？」
- 「知了笔记 2.0 卖多少钱？」

## 五、怎么用

### 日常使用

| 想做什么 | 怎么做 |
|---|---|
| 添加新知识 | 把文件丢进 `knowledge/` 对应领域目录后运行 `python ingest.py`；或在网页中上传文件、拖拽/选择整个目录入库。目录导入会保留中文名称和全部子目录；自定义拖拽入口合计最多 64 MB，原生点击选择入口默认每个文件最多 200 MB |
| 收藏一个网页 | 「上传文档」页的「🌐 添加网页」标签（需先在插件管理里安装网页入库插件）：粘贴 URL 一键抓取正文入库，之后和普通文档一样可被检索、引用 |
| 提问 | 在网页聊天框中直接输入问题 |
| 看答案出处 | 每个回答下方展开「📚 参考来源」，含领域、版本、状态标签和原文摘录 |
| 管理知识 | 网页里可完成：筛选、查看档案、**编辑档案**、重新入库、归档、恢复、移除 |
| 知识总结 | 知识管理台输入主题（如"RAG"），跨文档综合成一份带出处的总结 |
| 版本追溯 | 改文档重新入库自动升版本，旧版转 expired 留档；检索范围可切「包含归档与历史」 |
| 切换界面语言 | 「设置 → ⚙️ 通用设置」：简体中文 / 繁體中文 / English / 日本語，即时生效，只翻译界面，不影响知识内容与检索 |
| 学习 RAG 节点流转 | 调试模式（默认开启）下，每次回答附带 15 节点时间线；对照 [prd.md](prd.md) 第 2、3 节食用 |
| 检查系统状态 / 清空重建 | 网页「设置」菜单里统一操作 |

### 列举与统计问题的处理

- **目录统计**：如“知识库有多少份文件”“今年上传的文件有哪些”，在当前权限和筛选范围内滚动读取已入库文件元数据，按文档编号去重，不调用向量化或生成模型。默认只统计生效知识；“上传/入库”按入库时间筛选，其余日期问法按文件修改时间。支持今年、去年、指定年份、本月和上个月；未知内容条件会回到语义检索，不会悄悄忽略。
- **指定文档列举**：优先按文件名定位；未明确文件名时使用检索定位。读取目标文档的卡片，沿用部门权限、状态和版本限制，避免重新按普通 Top K 截断。
- **跨文档语义列举**：混合召回后按文档聚合，以标题、章节和代表性片段精排，再展开文档；不同文档的卡片轮流进入组装，减少长文档挤占其他来源。遵循精排开关与后端配置；MCP 仅检索模式允许本地精排，失败时不调用云端模型。

前端显示候选/匹配文档数、采用文档数和截断提示；MCP 在 `coverage_details` 返回同样的范围信息。目录完整扫描且完整展示时可返回 `complete`；语义列举最多返回 `unknown`，触及召回、展开或上下文预算时返回 `partial`。这些计数是文档数，不是问题中实体/条目的总数。

预算见 `.env.example` 的 `ENUM_*`：默认召回 50 张卡片、精排最多 24 篇、展开最多 12 篇、每篇最多 40 张，上下文最多 40 张/约 12000 tokens；目录最多扫描 50000 张卡片的元数据、展示 200 份文件。预算需要根据实际文档分布评估。这些参数控制首轮检索，不代表完整性保证；尚未对 120GB 文件进行压测。

### 单会话上下文管理


服务端会话按创建日期和数据库中的用户 ID 归档，例如 `storage/sessions/20261118/42/<session_id>.json`。跨天继续同一会话不改变目录，用户改名也不改变 ID。无归属旧记录放在 `anonymous/`；找不到原账户的记录使用 `account_<用户名哈希>/`，不将用户名直接拼入路径。目录归档与 JSON 归属校验共同隔离用户，同名新账户不能读取旧用户 ID 目录中的记录。全局会话锁和删除标记集中在 `storage/sessions/.locks/`。仅支持上述目录结构，不扫描旧目录，也不包含自动迁移或批量迁移逻辑。

保留每个会话一个 JSON 的原始消息、检索条件、来源快照、处理范围和回答记录，不引入跨会话记忆库或额外向量索引。这些 JSON 保存在运行 RAG 的服务端 `storage/sessions/`，浏览器不保存这一份会话文件。当前标签页用 URL 的 `session` 参数标识会话，刷新后按服务端登录身份检查归属并恢复；新建会话清空活动上下文。旧 JSON 没有摘要字段时仍可打开，摘要按需重建。会话文件读取、覆盖和前端删除均检查归属。未提供用户名的接口只能操作无归属的个人记录，不能查看或覆盖已归属用户的数据。新会话 ID 使用 128 位随机后缀；保存和删除使用线程锁与操作系统文件锁，将归属检查与原子写入放在同一临界区。同一会话的旧标签页只能追加到当前记录，发生分支冲突时明确提示，不静默覆盖；删除标记阻止旧标签页重新创建已删除的会话。当前文件锁方案针对单台服务端本地磁盘部署，不等同于多服务器分布式事务。

每次查询从当前会话原文中组装：近期对话、带消息索引的原话式增量摘要、最多两条相关旧消息、最近一次检索的来源身份及覆盖/停止状态。原始记录只保存一份，摘要状态另存消息索引、少量原话与前缀校验值，不再复制完整检索正文。历史助手回答与摘要不是知识证据，引用编号不能移用；知识事实仍由本轮检索核实。索引纪元、权限/手动筛选范围或用户身份变化时，旧助手摘要和旧检索结果不自动重放，同一会话内仍可核对的用户原话约束继续保留。

默认最近 4 轮优先保留，历史上下文合计约 6000 tokens（独立于检索资料预算）；新增且离开近期窗口的旧消息达到约 4000 tokens 才进行一次有上限、无重试的摘要调用，摘要最多约 1200 tokens。摘要内容须逐字对应原消息，失败退回原话摘录并推进压缩进度，避免反复为同一段失败摘要计费。超长近期消息保留首尾并标注中间省略。每轮按当前问题在本会话旧消息中做轻量词项匹配，最多召回 2 条；既不扫描其他会话文件，也不创建跨会话记忆。

同一份有预算的会话线索交给查询理解、回答生成和列举提取/补查。前端与调试记录展示摘要状态、召回消息索引、上下文用量及失效信息；摘要模型用量和上下文准备耗时单列。回答缓存按用户、会话、完整历史摘要哈希、筛选、模型开关和索引纪元隔离；没有会话标识的历史请求不使用共享对话缓存。模型/历史上下文仍需与检索资料和输出一起适配实际模型窗口，本项目的 token 数为估算值。

设计参考 [Anthropic 的上下文压缩与按需取用建议](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)及 [LangChain 的单线程短期记忆](https://docs.langchain.com/oss/python/langchain/short-term-memory)，采用现有 Python/JSON 实现，没有为此增加框架依赖。公司业务样本仍需检验长期对话中的约束保持和摘要质量。

### 分批提取与多轮补查（列举第二阶段）

生成模式默认启用 `ENUM_STAGE2_ENABLED=true`，只对指定文档/跨文档列举生效；普通问答与目录统计保持原路径。MCP 仅证据模式不执行模型提取与规划，`stage2.reason=evidence_only` 明确说明；回答模式返回结构化 `items`、来源与 `coverage_details`。

先按游标分批读取首轮选定文档的卡片，长卡片再带少量重叠分段。模型提取名称、原文和来源编号，代码校验名称和引用确实出现在该批原文中，拒绝伪造来源和改写的引文。相同原文的同名条目，或具有同一明确原文编号的实体可合并并保留出处；同名不同证据的条目保留为待核实记录，记录数不等于唯一实体总数。原文校验是可溯源校验，仍需样本评估模型对问题相关性、否定语义和实体身份的判断。

跨文档列举再根据已有条目规划同义词等补查线索，重新检索、按开关精排、读取新文档、提取汇总。每轮服务端沿用最初的部门权限、状态、版本和日期等过滤条件，规划器不能修改过滤器。已处理文档和已用查询不会重复处理。指定文档列举只读取选定文档，不向全库扩展。

默认最多补查 2 轮、每轮 2 个查询，连续 2 轮无新增条目可停止；提取、规划和阶段内的 LLM 精排共用最多 12 次调用、约 32000 输入输出 tokens、90 秒的预算，同时限制最多 240 张卡片、24 篇文档、120 条记录。时间在操作边界检查，模型请求使用剩余时间且禁重试；网络读操作有超时，本地精排/关键词计算完成后再检查预算，因此耗时是软上限。预算不包含首轮检索与精排、Query 理解或回答质量评估。

最终清单直接从通过原文校验的结构化记录逐条生成，避免再次自由总结漏项。前端显示批次/补查轮数及停止原因，用量和耗时单列；结果与引用随会话保存。达到预算、部分失败或无效证据时明确 `partial`，不丢掉已确认记录；提取完全失败则退回首轮资料生成并提示。没有新线索或连续无新增结果也不证明全库已查全，语义列举不会返回 `complete`。各项预算均可在 `.env` 的 `ENUM_*` 调整，需用公司脱敏样本验证漏项、误列、去重准确率和成本后再扩大规模。

### 网页入库（插件）是怎么工作的

网页入库是 V3 插件系统的第一个输入源扩展，它**复用**而不是绕开入库流水线：

1. **安装**：「插件」菜单里安装「网页入库」插件（`src/web_fetcher.py`）；
2. **入口**：安装后「📤 上传文档」页自动多出「🌐 添加网页」标签，输入 URL 并选择领域（默认参考资料）；
3. **抓取与清洗**：`web_fetcher` 拉取 HTML 后剔除导航/页眉/页脚/脚本，把标题层级转成 Markdown，合并过短的段落；
4. **入库**：新网页直接保存到所选领域（例如 `knowledge/reference/`），Markdown 文件头记录 `source_url`。已有网址重抓时沿用原快照路径和版本记录；
5. **检索**：网页与普通文档共用向量和 BM25 检索，回答时同样在「📚 参考来源」中标注出处；
6. **卸载安全**：卸载插件只是隐藏入口，已入库的网页知识卡片不受影响。

### 给 Agent 用：MCP 接口（V3.3 新增）

除了给人用的 Web 界面，本 RAG 还能作为**工具**接入任何支持 MCP（Model Context Protocol）
的 Agent（Claude Desktop、Cursor、ZCode 等）——Agent 会自动调用你的个人知识库回答问题。

**工具集**（按 `MCP_MODE` 注册：`query` 提供 search/status，`answer` 提供 qa/digest/status；两种模式均提供 get_document/list_documents）：

| 工具 | 作用 | 是否需要 LLM |
|---|---|---|
| `knowledge_qa` | 基于知识库问答，返回带来源引用的答案（支持多轮 `history` 与领域/状态/文档类型过滤） | 需要 |
| `knowledge_search` | 只检索不生成，返回片段与相关度（零生成成本） | **不需要** |
| `knowledge_digest` | 跨文档主题总结 | 需要 |
| `get_document` | 按编号读取全文/分页片段，始终仅返回 active 且有权限的文档 | **不需要** |
| `list_documents` | 按领域/状态/文档类型及权限枚举目录（默认 active） | **不需要** |
| `knowledge_status` | 服务就绪检查（向量库 / 向量化模型 / LLM Key / 卡片数） | **不需要** |

五个内容工具均新增可选关键字参数 `doc_type`，原有位置参数（包括 `ctx`）顺序保持不变。示例参数：`knowledge_search(question="建设目标", domain="work", doc_type="一期方案")`，或 `list_documents(doc_type="__unclassified__")`。类型标签去首尾空白后精确匹配，无隐式别名合并；省略/留空/`all` 不限类型，`__unclassified__` 仅查旧缺失/`null`/空值。`get_document` 的类型过滤不会放宽 active-only 或部门权限规则。返回的来源、matches、全文/片段文档档案和目录行均包含 `doc_type`（旧文档为空字符串）。

五个内容工具也接受可选参数 `project`（完整项目名称、唯一简称或整数 ID）和 `business_direction`（主业务方向名称、字母编号或整数 ID）。例如 `list_documents(business_direction="低空经济", department="研发部")`，或 `knowledge_search(question="验收要求", project="低空监管平台")`。同时提供时取交集，继续叠加部门权限、领域、状态及文档类型。简称只兼容项目名称常用后缀的变体，有多个匹配时请改用完整名称或 ID。方向按项目主档实时解析。项目或方向不存在会返回具体错误，方向下没有项目或交集为空会返回空结果。文档结果带 `project_id`，未挂项目为 `null`。

`knowledge_search` 和 `knowledge_qa` 由调用方管理会话。优先传本轮问题和已确认的 `project`，需要服务端消解指代时传相关 `history`。依赖指代的问题中，如果最近一条用户消息明确切换到了另一个项目，接口返回 `coverage_details.scope_issue=conflict`，调用方应核对参数后重试。后台员工检索日志详情记录入参形态、采用的历史条数、项目范围来源和范围状态。诊断字段不保存历史正文。

**接入方式**（以 ZCode / Claude Desktop 为例，写入其 MCP 配置）：

```json
{
  "mcpServers": {
    "sky-personal-rag": {
      "command": "/Users/你的用户名/sky-rag-stu/.venv/bin/python",
      "args": ["/Users/你的用户名/sky-rag-stu/src/mcp_server.py"]
    }
  }
}
```

**前置条件**：调用前需保持 **Qdrant 与 Ollama 运行**（`./start.sh` 或 `bash scripts/start_qdrant.sh`）；
不确定时先让 Agent 调 `knowledge_status` 自检。

**设计说明**：MCP 是纯外壳（`src/mcp_server.py`），只 import 既有问答入口，
**核心 RAG 流水线与 Web 界面零改动**；服务无状态（会话历史由 Agent 传入），
Streamlit 界面照常可用。工具描述内置三层行为契约：何时必须调用、检索结果的权威性、
查不到时的边界——让 Agent 无需额外配置即可正确使用。

### 调参

所有参数都在 `.env` 里改，改完重新入库即可：

| 参数 | 含义 | 默认 |
|---|---|---|
| `CHUNK_SIZE` | 每张知识卡片的目标长度（字符） | 600 |
| `CHUNK_OVERLAP` | 相邻卡片之间重复多少（防切断语义） | 100 |
| `TOP_K` | 每次提问召回几张卡片 | 5 |
| `CONTEXT_MAX_CHARS` | 给大模型看的资料总字数上限 | 6000 |
| `CONTEXT_MAX_PER_DOC` | 同一文档最多进入回答的卡片数（保持来源多样） | 3 |
| `AUTO_TAG` | 入库时 LLM 自动补全主题/标签（V3，每文件多用一次 LLM 调用） | true |
| `QUERY_UNDERSTANDING` | Query 理解/改写开关（V2，多用一次 LLM 调用） | true |
| `HYBRID_SEARCH` | 混合检索开关（向量 + BM25 关键词，V2） | true |
| `RERANK_ENABLED` | Rerank 精排开关（V2，多用一次 LLM 调用） | true |
| `RERANK_RECALL_K` | 精排前的宽召回候选数 | 10 |
| `LLM_TEMPERATURE` | 回答的稳定度（越小越严谨） | 0.2 |

> 💡 V2 三个开关的经验法则：日常问答开「混合检索」就够了（免费提准）；要处理口语化提问和归档意图时开「Query 理解」；对回答质量要求高、不在乎多几秒延迟时开「Rerank」。三个开关都在网页「设置 → 检索设置」里可随时切换。

## 六、评测：怎么知道系统好不好

`eval_set.json` 是一份考卷：每道题 = 问题 + 标准答案在哪个文件 + 答案该包含的关键词。
其中还有几道「知识库里根本没有答案」的陷阱题，专门考系统会不会老实说不知道。

```bash
python eval.py --no-llm    # 先只考检索（免费，秒出）
python eval.py             # 再考完整问答
python eval.py --save      # 结果存档到 storage/
```

看三个指标：

- **检索命中率**：标准来源有没有进入召回的前几名 —— 检索是地基；
- **回答有据率**：答案里是否真的用上了资料；
- **无答案拒答率**：没资料时会不会胡编 —— 这是 RAG 的底线。

### V2 新增：难题考卷 + 四配置对比

- [eval_set_hard.json](eval_set_hard.json) 是 18 道**难题考卷**，按五类设计，分别考察 V2 新增节点：
  口语化指代（考 Query 改写）、专有名词/编号（考 BM25）、归档意图（考 status 推断）、
  精排干扰（考 Rerank）、无答案陷阱（考拒答底线）；
- `eval_compare.py` 让同一份考卷在 **4 种配置**下跑分（V1 基线 / +混合检索 / +Query 理解 / V2 全开），
  输出命中率、有据率、拒答率、平均耗时、LLM 调用数的对比表，报告存入 storage/：

```bash
python eval_compare.py --eval-set eval_set_hard.json --save   # 难题考卷四配置对比
```

> V1 基线在难题考卷上的检索命中率约 67%，V2 全开 100%——每个节点的贡献与代价
> （耗时、LLM 调用数）一目了然。参考分析见 prd.md 第 8.4 节。

> 你应该用**自己的知识**出 20~50 道题替换示例考卷——用真实问题评出来的结果才有意义。
> 检索不命中多 → 调大 `TOP_K` 或调 `CHUNK_SIZE`；改一个参数、重跑一次评测，对比分数。

```text
sky-rag-stu/
├── knowledge/                 📁 你的知识文件放这里（按 work/learning/life/projects/reference/archive 分类）
├── storage/                   📁 本地运行数据（向量库数据、评测报告），已 gitignore
│
├── src/                       📁 核心源码：一条流水线上的各个节点
│   ├── config.py              ⚙️  配置中心：读 .env，全项目共用
│   ├── metadata.py            🗂  知识库管理：目录→领域/主题、文档身份证、Front Matter
```

## 八、常见问题（FAQ）

**Q：界面显示「连不上本地 Ollama」？**
先在终端跑 `ollama list`，能看到模型列表就说明 Ollama 正常；再检查 `.env` 里的 `OLLAMA_URL`（默认 `http://localhost:11434`）。

**Q：如何确认回答使用的是本地 Ollama，而不是云端模型？**
检查 `.env` 中的 `LLM_BASE_URL` 是否为 `http://localhost:11434/v1`，然后打开网页的「系统状态」；大模型一项显示“本地 Ollama”即表示配置生效。

**Q：本地模型为什么仍要填写 `LLM_API_KEY`？**
Ollama 本身不验证 API Key。`LLM_API_KEY=ollama-local` 只是兼容 OpenAI 客户端的占位值，不是真实密钥。

**Q：显示「找不到模型 qwen3-embedding:4b」？**
运行 `ollama pull qwen3-embedding:4b`。如果换成其他 embedding 模型，改 `.env` 里的 `EMBEDDING_MODEL` 后必须**重建知识库**（不同模型的指纹规格不同，不能混放）。

**Q：连不上 Qdrant / 系统状态里 Qdrant 是红灯？**
先运行 `bash scripts/start_qdrant.sh`，确认 6333 端口没被占用。每次重启电脑后需要重新启动它。

**Q：换了 LLM 服务商要改哪里？**
只改 `.env` 里 `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL` 三行，代码不用动。

**Q：某个文件入库失败了？**
入库日志会写明原因。最常见的是加密 PDF 和扫描版 PDF（图片型，没有文字层），后者需要 OCR 能力，属于后续版本规划。

**Q：回答不准确 / 检索不到，先调什么？**
按顺序试：调大 `TOP_K` → 调 `CHUNK_SIZE`（300~800 之间试）→ 调 `CHUNK_OVERLAP`。每改一次跑一遍 `python eval.py --no-llm` 对比命中率。

**Q：我明明有相关文档，为什么检索不到？**
先看两件事：① 文件是否已经重新入库（`python ingest.py`）；② 文件是否放在 `knowledge/archive/` 里——归档内容默认不参与回答，把检索范围切到「包含归档」即可。

**Q：数据安全吗？**
知识文件、向量和运行数据都保存在本机。使用云端大模型时，提问和检索到的相关片段会发送给所选服务商；使用本地 Ollama 大模型时，问答全程在本机完成，内容不会发送到云端。

**Q：一个问题里问了多件事，只回答了一半？**
V3.4 起支持**查询拆分**：Query 理解会自动把复合问题拆成多个子查询分别召回；V3.5 起合并时每个子查询**保底配额**进候选池，弱势子问题不再被挤光。若仍偶发只答一半，先确认「检索设置」里的 Query 理解开关已开启（拆分依赖它）；偶发失败多因 LLM 拆分波动，重问一次通常恢复，机制说明见 realize.md B3.5.1。

**Q：MCP 接入 Agent 后，Agent 不主动查知识库？**
MCP 工具描述内置了触发条件（涉及简历/登记表/笔记等私有资料时自动调用），新会话生效。临时提示一句“查我的知识库”也能立即触发；排查顺序：确认 MCP 已连接 → 新开会话 → 显式提到“我的知识库”。

**Q：开了代理软件后，连不上 Qdrant / 启动误报超时？**
代理变量（HTTP_PROXY/ALL_PROXY）会劫持本机请求。`start.sh` 已自动摘除；手动跑 `python ingest.py` 或 MCP 前先 `unset http_proxy https_proxy all_proxy ALL_PROXY`。

**Q：评测命中率突然变成 0？**
评测集必须与知识库内容同步——知识库更换内容后，原考卷的期望来源文件可能已不存在。按新资料重建评测集（参考 `eval_set.json` 的格式）。

**Q：某个网页的回答总说“内容不完整”？**
少数网页快照的正文可能有残句或截断。可以用快照文件头的 `source_url` 打开原文核对。
