## Q1：我们现在的切片规则是什么（详细）？

**四层漏斗，逐层收窄**（参数 CHUNK_SIZE=600、CHUNK_OVERLAP=100，单位是字符）：

```
整篇文档
 ├─ ① 分页：PDF 页码标记切段（记录起始页码，跨页段标「3-4」）
 │    └─ ② 章节：Markdown 标题切（#~######），维护层级栈
 │         └─ ③ 段落：章节内按空行切段
 │              └─ ④ 打包：攒段落 ≤600 字封口成卡
```

**第④层三种情况**：段落 ≤600 顺序攒；单段落超长先按句子边界切（。！？；和换行）再打包；整句都超长才按字符硬切。

**Overlap 规则**：新卡开头带上一张卡结尾的 100 字；重叠起点落在半句话中间时向后对齐到行边界；章节是硬边界（跨章节不重叠）。

**参数保护**：size 最小 100；overlap ≤ size 的一半。

**每张卡片生成**：chunk_id（文档ID+版本+序号）、point_id（uuid5 确定性哈希——同文档同版本重复入库原地覆盖永不重复）、继承全部档案 + section/section_path/page。

## Q2：600 字符，对英文是 600 个字母还是单词？

**600 个字符**（len() 计数，空格标点也算）。

- 中文：600 字 ≈ 400~500 词，信息密度高
- 英文：600 字符 ≈ **100~120 个单词**，语义上明显更碎

中英混排影响不大；**英文内容变多时建议 CHUNK_SIZE 调到 1500~2000**（改完需重新入库）。

## Q3：业界的切片是按字数还是 token？

三种流派 + 一个正交维度：

| 流派 | 计量 | 代表 | 适用 |
|---|---|---|---|
| 字符数 | len() ≤ N | CharacterTextSplitter | 简单，中文场景够用（字符≈token） |
| **Token 数**（工业主流） | 分词器计数 | TokenTextSplitter 等 | 多语言、与模型上限/成本精确对齐 |
| 语义切分 | 相似度骤降处切 | SemanticChunker | 质量优先，成本高 |
| 结构切分（正交） | 按标题/段落定切点 | MarkdownHeaderTextSplitter | 「在哪切」，与「用多大」组合用 |

**工业级要点不是"用 token 硬切"**，而是：切点仍按语义/结构边界 + 大小与 embedding 模型输入上限对齐 + 全库一致可复现。

## Q4：那我们要不要换成 token 切块？

**现在不换**（已记入观察清单）。理由：中文"字符≈token"换过去收益≈0；当前 600 字 ≈ 480~600 tokens 远低于 embedding 上限，无截断风险；换计数 = 全库重建 + 评测重跑。

**触发信号**（满足任一再动手）：① 英文/多语言内容占比上升；② 更换 embedding 模型且有严格 token 上限；③ 需卡片级成本核算。

## Q5：embedding 模型指什么？工业级是不是必须 token 切？

- **embedding 模型 = 向量模型**（同一东西不同叫法），职责：把文本变成向量，让"语义相近"变成"数字距离近"。**别和 LLM 混淆**：embedding 管"找得准"，LLM 管"说得好"。
- 工业级：主流是 token 维度，但准确说是"**token 预算 + 语义边界**"的组合——切点仍按语义边界，纯 token 硬切也是反模式。

## 今日核心认知

1. **600 上限只保证"不超过"，不负责"切在哪"**——切点由语义边界决定
2. **Overlap 是切片与相邻补全的配套冗余**：切片时故意重复，检索后拼回去重
3. **换 embedding 模型 = 全库重建**——两套语义空间的数字不可比较
