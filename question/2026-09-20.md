## Q1：评测的目的是什么？整个流程是什么？

- **一句话目标**：RAG 的效果 =「一堆参数 + 一堆开关」组合出来的函数。评测把"我感觉变好了"变成"数字变好了/变坏了"——它是调参和改代码时唯一可靠的依据。
- **四个目标**（重要性从高到低）：
  1. **回归保护**：参数是联动的，改 A 可能弄坏 B，评测卷就是回归测试；
  2. **量化体检**："感觉挺准"不是工程语言，"命中率 11/12"才是；
  3. **调参决策**：凭感觉选参数叫赌博，跑评测对比叫实验；
  4. **防幻觉底线**：考卷里专门有 should_refuse 题，测系统敢不敢说"没有"。

**完整流程**：出卷（人工，四要素）→ 跑卷（自动，逐题走真实流水线）→ 判卷（规则打分）→ 出报告 → 对比使用。

**四要素**：question（问什么）/ expected_source（应命中哪个文件）/ expect_keywords（答案必须含的关键词）/ should_refuse（应该拒答）。

**三项指标**：检索命中率（考检索及之前）/ 答案质量（考整条流水线）/ 拒答能力（考防幻觉）。

**两套考卷分工**：基础卷 = 体检（整体水位）；困难卷 = 分科诊断（每题标注考察节点，配合 eval_compare.py 做开关对比）。

## Q2：评测是根据量化结果修改参数，让回答更准确，对吧？

对，但三点要精确：

1. **"修改"不只是调参数**——准确性提升的大头来自**修 bug**（如表格空格归一化、缓存键缺历史），纯调参收益占小头。正确顺序："先修对、再调优"。
2. **量化结果最大的价值不是打分，是定位**：命中率低 → 问题在检索之前；命中了但答案差 → 问题在组装/生成；该拒不拒 → 底线环节。错题是用来**指认环节**的。
3. **目标是多目标平衡**：准确 / 便宜 / 快 / 不幻觉之间取舍，个人知识库通常"不幻觉 + 不漏"优先。

**闭环最后一环**：改完必须再跑一次评测，确认目标指标涨了、其他没跌——否则只是"换了一组参数"，不是"变好了"。

## Q3：Query 理解补上 enumeration 后，LLM 输出要多一个字段吗？

是。Query 理解的 JSON 输出新增 `enumeration`（布尔）：LLM 语义判断该问题是否为计数/列举类（不限措辞），判定为 true 时流水线自动"三旋钮同拧"：

- 召回数量翻倍（5→10）
- 上下文条数翻倍（5→10）
- 单文档上限放开（3→不限）

**为什么三个一起拧**：只扩召回不扩上下文（组装时被丢弃）、或单文档上限没放开（同文档条目被截断），都会让计数答案偏小。

**双通道判定**：LLM 语义识别为主（「工作变动过多少回」这类词表外问法也能识别），关键词词表（几份/几段/有哪些/全部…）为兜底（Query 理解关闭或解析失败时依然生效）。

## 今日核心认知

1. **评测之于 RAG，如体测之于健身**——没有它，所有的"练"不知道是在变强还是变弱
2. **先修对，再调优**——参数微调的收益远小于把 bug 修对
3. **错题是指认环节的探针**——按指标分维度拆，才能定位到具体节点
