# 第一部分：索引与向量库（9 问）

## Q1：HNSW 指的是什么？

**Hierarchical Navigable Small World（分层可导航小世界图）**——向量数据库最主流的检索算法（Qdrant/Milvus/Elasticsearch 底层）。

- **解决的问题**：精确检索要和全库每张卡片算距离，数据量大时不可接受；HNSW 只在一张精心组织的图上"导航"到大致最近的邻居，**牺牲一点精确换毫秒级稳定速度**——这就是"近似最近邻（ANN）"
- **名字=原理**：Small World（图上任意两点少跳可达）+ Hierarchical（多层金字塔：顶层稀疏跨越大方向，底层稠密全量精比较）
- **查询**：从顶层入口贪心走向更近的邻居，走不动就下一层——像查地图先全国再省道再街道
- **对当前规模**：76 张卡暴力检索也瞬间完成，HNSW 的价值是"未来扩容不换引擎"

## Q2：向量数据库检索的本质就是 HNSW 对吧？

**不完全是**——把"本质"和"最流行的实现手段"混在一起了。

向量检索的本质 = **高维空间的相似度近邻搜索**，由两个独立部分组成：

| 层 | 回答的问题 | 我们的选型 |
|---|---|---|
| 相似度度量（算什么） | "像不像"怎么量化 | COSINE 余弦 |
| 搜索策略（怎么找） | 按什么结构找 | HNSW 索引 |

HNSW 只是搜索策略的一种。其他索引家族：IVF（聚类分桶）、PQ/SQ（量化压缩）、DiskANN（磁盘）、暴力精确检索（小规模毫秒级且 100% 准）。

**另注意**：我们的另一条检索通道 BM25 与 HNSW 完全无关（倒排关键词索引）。小集合时 Qdrant 甚至可能直接走精确全扫——HNSW 是规模化时的加速结构，不是检索的定义。

## Q3：我们建立了两套索引——向量索引 + 关键词索引，对吧？

接近了，**准确说是三类**：

| # | 索引 | 时机 | 支撑什么 |
|---|---|---|---|
| ① | 向量索引（HNSW） | 建集合时 | 向量通道相似度搜索 |
| ② | **Payload 过滤索引**（11 字段：9 keyword + 2 datetime） | 建集合时 | Metadata 过滤 + 管理操作定位 |
| ③ | BM25 关键词索引 | **每次查询时内存现建**（带缓存） | 关键词通道 |

**最容易被漏掉的是②**——"限定领域""仅 active""最近三个月"能毫秒级生效全靠它。

**③最特殊**：BM25 不是入库时建的，而是查询时现建——因为 BM25 需要"词在全部文档中的分布"（IDF），现建保证与库内数据实时一致；个人库规模下毫秒级完成。混合策略：**持久索引查向量、即时索引查关键词**。

## Q4：两路检索都通过索引进行，对吧？

对，且是三套索引同时服务：

- 路 1 语义检索：问题向量 → ① HNSW（叠加 ② Payload 过滤，过滤发生在搜索过程中）
- 路 2 全文检索：② Payload 先圈定语料 → ③ 现建 BM25 打分（过滤发生在建索引之前）
- 过滤条件两路都通过 ② Payload 索引生效——不是检索完再人工筛

## Q5：Payload 过滤索引的"管理操作精确定位"指什么？

指管理台上"针对某一个文件"的操作，都要先按 document_id 精确圈中该文件的全部卡片：

1. 查看卡片原文（document_id 圈中）
2. 重新入库前"旧版本批量转 expired"
3. 移除知识（批量删 N 个文件的全部卡片）
4. 入库时的孤儿清理（台账有、磁盘无 → 清向量）

没有索引时这些操作要全库遍历——数据量大后管理台会变卡。

## Q6：索引怎么理解？传统索引和向量索引相同吗？

**本质相同**（都是"用空间换时间的预建查找结构"），**实现完全不同**（因为解决的问题不同）：

| | 传统索引（B+Tree） | 向量索引（HNSW） |
|---|---|---|
| 前提 | 数据**可排序** | 只有**距离/相似度** |
| 查询类型 | 等值、范围 | 相似度 Top K |
| 结果 | 100% 精确 | 近似（95%~99%） |
| 类比 | 字典部首目录（按序定位） | 地图导航（先高速后街道） |

高维向量**无法排序**（"哪个更大"没有意义），所以 B+Tree 立身之本失效，必须发明新结构。

## Q7：我们建立的索引是 document_id 对吧？

**不对——document_id 只是 11 个被索引字段之一**。完整清单：

- ① HNSW：建在 2560 维向量本体上
- ② Payload 索引：document_id、source、domain、category、topic、tags、status、version、file_type（9 keyword）+ created_at、updated_at（2 datetime）
- ③ BM25：建在卡片全文分词上

## Q8：通俗讲一下索引是什么，为什么快？

**字典比喻**：

- 没索引：查"熊"字从第一页翻起，平均翻半本
- 有索引：部首目录写着"灬部 → 第 1200 页"，直接翻到

**为什么快**：目录是**提前整理好的结构**，查找时顺着结构跳到目标区域，不用逐条比对。

**索引不是魔法，是提前付出的劳动**：入库时多花时间建结构、多占存储（"已创建集合""建立过滤索引"日志就是付这笔劳动），提问时的毫秒级响应就是收利息。

（见 Q7——同一天的追问，纠正为三套索引、11 个字段。）

# 第二部分：MCP 接口（从概念到三层契约）

## Q10：RAG 加到 Agent 里，是不是要开放一个能力/接口，当做 Agent 的一个节点？

对。现有入口（网页/命令行）都是给人用的；Agent 需要**程序化、结构化、低延迟**的接口。三档方案：

1. HTTP API（最简单）
2. **MCP Server（业界标准，推荐）**——Claude/Cursor/ZCode 原生支持，接入方零代码
3. 细粒度工具拆分（qa/search/digest 分开，让 Agent 自己决定调哪个）

## Q11：封装 MCP Server 时为什么强调零侵入？

封装只 import 既有入口（answer_question），**核心流水线、Web 界面、数据格式一行不改**——Web 和 MCP 是同一内核的两个外壳，互不影响。

**无状态设计**：会话历史由 Agent 通过 history 参数传入，服务本身不保存——可被多 Agent/多会话并发使用且不串号。

## Q12：Agent 如何知道该调用 MCP 工具？（实测：不提"知识库"它就不调）

工具的 `description` 通过 `tools/list` 下发给 Agent 的 LLM，是它选择工具的**唯一依据**——纯语义判断，概率性。

**解决哲学：工具的使用时机说明跟着工具走**（写进描述），而不是要求每个接入的 Agent 配本地规则——否则 N 个客户 × N 份规则，违背 MCP 可复用性。

最终形成**四层行为契约**：

1. **触发条件**：私有资料类问题必须调用（描述里列明简历/登记表/笔记等）
2. **权威声明**：检索结果即完整来源，禁止另行搜索磁盘
3. **未命中边界**：查不到时如实告知，不替答不转搜，交给用户决定
4. **参数用法**：history / domain / top_k 等

**代价认知**：描述是每个会话加载的常驻上下文成本——已设定停止线，不无限堆砌。

## Q13：权威声明改了什么文件？如何声明的？

只改 `src/mcp_server.py`——三个工具（qa/search/digest）的 docstring 各插入：

> 权威声明：知识库检索结果即用户个人资料的权威完整来源——基于检索结果回答即可，除非用户明确要求，不要额外搜索用户磁盘/文件系统来"确认完整性"。

search 额外加：枚举类问题以检索结果为准作答。措辞用意：①"权威完整来源"打消"可能有遗漏"的念头；②"除非用户明确要求"留合法出口；③把禁止项写具体。

## Q14：知识库查不到时，是不是也要定义边界？

是——补上了逻辑缺口：权威声明只说"库=完整来源"，没说"查不到时怎么办"，Agent 会自作主张换途径。新增**未命中边界**：

> 检索结果为空或明显不相关时，如实告知用户"知识库中没有找到相关内容"，不要用模型通用知识替答、也不要转而搜索磁盘；由用户决定是否换用其他途径。

**行为闭环三层**：① 何时必须调用 → ② 结果的权威性 → ③ 查不到时的边界。第③层同时挡住向下越界（编造）和向外越界（乱找），把选择权还给用户。

## Q15：这个边界有没有必要？权重分数多少？

**7/10，值得保留但属补漏型而非关键型**：

| 子句 | 边际价值 | 理由 |
|---|---|---|
| 不用通用知识替答 | 低 | RAG prompt 与返回 payload 已带拒答文本，双保险已有 |
| 不转搜磁盘 | **高** | 实测真实行为，无其他层能挡 |
| 由用户决定换途径 | 中 | 给 Agent 明确出口，避免卡住 |

成本侧：描述膨胀是常驻上下文成本——已设定停止线（描述调优到此为止）。最弱措辞："资料不足"偏模糊，可收紧为"明显不相关"减少误伤。

## Q16：重新入库吗？（文件名修复后）

不需要——修复流程的最后一步已替用户全量重建（9 文件 155 卡片）。唯一要做的是重启 ZCode 会话让 MCP 重连。

# 第三部分：评测重建

## Q17：困难卷要不要一起重建？是什么意思？

两个评测集是「体检」和「分科诊断」的关系：

- **基础卷**：13 道常规题，看整体水位（命中率/有据率/拒答率）
- **困难卷**：每题**故意设计成只有某个节点发力才能答对**，并标注考察节点（Query 理解改写 / BM25 精确匹配 / Rerank 精排 / 计数扩容 / 证据门控…）

用途：配合 `eval_compare.py` 做**开关配置对比**——改哪个节点后能看出影响的是谁。基础卷只能告诉你"整体没坏"，回答不了"该开哪个开关"。

重建 = 把针对已丢失示例文档的旧题，改写成针对真实资料的新题，每题继续标注考察节点。

## Q18：重建后的基线

| | 基础卷 13 题 | 困难卷 16 题（8 类节点） |
|---|---|---|
| 检索命中率 | 11/11 = 100% | 13/13 = 100% |
| 回答有据率 | 11/11 = 100% | 13/13 = 100% |
| 拒答率 | 2/2 = 100% | 3/3 = 100% |

**出题时发现的判卷边界**：① expected_source 必须唯一（简历与登记表内容高度重叠，需选各自独有事实）；② 规则判卷对措辞变化有盲区（"10年"vs"十年"，已换成表述干脆的题）。

## 今日核心认知

1. **HNSW 是手段不是本质**——本质是相似度近邻搜索
2. **索引=提前付出的劳动**——三套索引各自服务一种查找需求
3. **MCP 工具描述就是产品边界**——工具的使用时机跟着工具走
4. **评测集必须与真实知识库同步**——针对丢失文档的考卷，命中率恒为 0
